1 · LEXICAL ANALYSIS

A single left-to-right scan classifies each piece as NUMBER, VARIABLE, OPERATOR, LPAREN or RPAREN, after normalizing − × ÷.

Unary-minus rule: a “-” is unary if it is the first token, or follows “(” or another operator.

It also checks brackets, empty “()”, adjacent operands such as a b, and a trailing operator.

O(n)single pass

2 · SHUNTING-YARD

Dijkstra’s algorithm moves operands straight to the output and keeps operators on a stack, popping by precedence.

OperatorPrecedenceAssociativity

* /2left

3 · EXPRESSION TREE

Postfix is read once with a stack of subtrees. An operand becomes a leaf; a binary operator pops the right child, then the left, and pushes the new node back.

Unary minus pops one operand and stores it as its right child. Exactly one node must remain at the end.

stackbinary tree

4 · POSTORDER EVALUATION

A depth-first walk visits Left → Right → Root, so operands are always ready before their operator. Each step is logged.

Division checks the divisor: if |d| < 10⁻¹² it stops with a division-by-zero error.

recursionO(n)

TREE DRAWING

Leaves are placed left to right in slots sized by their label width, and each parent is centred above its children. Depth sets the row, so wide labels such as a=12.5 never collide.

The problem

Why the same formula gave different answers at the observatory, and why nobody could tell where it went wrong.

PROBLEM STATEMENT

At a small observatory, volunteers use mathematical expressions to calculate nightly measurements. Different volunteers sometimes obtain different results for the same expression. Their old calculator displays only the final answer, so no one can tell where a calculation went wrong.

Task: develop an Expression Evaluation and Visualization System that produces both an accurate result and an understandable record of how it was obtained.

ROOT CAUSE 1 · AMBIGUOUS RULES

Nobody had written down how an expression must be read. Each volunteer applied their own habits for operator order, grouping, minus signs and division, so one formula had several valid-looking readings.

ROOT CAUSE 2 · HIDDEN WORK

The old calculator showed only the final number. Two different answers could not be compared step by step, so the mistake could not be located, only suspected.

Different answers came from unwritten rules (precedence, associativity, unary minus, real division) and unchecked input (brackets, numbers, variables, zero divisors), and the lack of any record hid which of these caused the gap.

Approach & solution

How we turned an unreliable one-line answer into a result you can verify at every step.

How we got here

1 · FIND WHY ANSWERS DIFFER

We listed every way one expression can be read differently (the table on the Problem page) and grouped them into unwritten rules and unchecked input.

2 · WRITE THE RULES DOWN

One fixed grammar: a precedence table, left-associative binary operators, right-associative unary minus, real division. Now there is exactly one correct reading.

3 · SPLIT INTO STAGES

Instead of one opaque calculation, four small stages: tokenize, convert to postfix, build a tree, evaluate it. Each stage has one job and can be checked alone.

4 · RECORD EVERY STAGE

Each stage leaves evidence: a token and stack trace, a drawn tree and a calculation log. The answer is the last line of a visible story.

5 · VALIDATE BEFORE COMPUTING

Bad input is rejected early with its position and reason, so nothing is silently guessed. Division by zero stops the run instead of producing noise.

6 · COMPARE, DON’T ARGUE

Two volunteers with different answers can compare traces. The first line where they differ is the mistake.
